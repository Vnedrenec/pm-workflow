# Роли конвейера

Слой 2 регламента воркспейса. Формат правила — `README.md`; адрес правила — `roles.md#<якорь>`. Источник текста — снимок инструкций PM на 18.09.2026 (в приватном архиве), раздел Roles.

Работа, требующая кода или проектирования, идёт карточкой-родителем со стадиями-подзадачами. Родитель назначен на PM; подзадачи — на исполнителей. Стадии не планируются заранее одним списком: PM достраивает очередь реактивно — сервер будит его на закрытии каждого барьера, он читает результат и решает, какой будет следующая стадия. Число кругов ревью заранее не известно — это цикл, а не линия (`review-cycle.md`).

### Таблица ролей `[ревью: PM @ создание стадии]`
<a id="roles-table"></a>

| Стадия | Исполнитель | Что делает |
|---|---|---|
| approach fork | Architect | собирает независимые мнения веером моделей, решает сам |
| plan (постановка) | Architect | спецификация, по которой будет работать другой агент |
| code | Builder | реализация по постановке |
| mechanical edit | Mechanic | переименования, опечатки, форматирование; боковая ветка, не стадия |
| audit | Reviewer | круг ревью; состав аудиторов подбирает сам |
| technical verdict | Architect | какие находки реальны, какие блокируют |
| scope change | **владелец** | находка требует переработки объёма — решает он, не Architect |
| acceptance | **владелец** | `in_review → done` на родителе |

Постановку пишет Architect (роль — отсюда); путь файла постановки — конвенция проекта (слой 3, напр. `docs/superpowers/plans/` в репозитории проекта).

Инцидент: нет

### Конфликты интересов: автор ≠ проверяющий `[ревью: PM @ создание стадии]`
<a id="author-not-verifier"></a>

Reviewer не консультирует по замыслу: аудировать то, что помогал проектировать, — конфликт интересов. Architect не аудирует свой план и свои находки. Builder не рассылает свой дифф моделям на ревью (см. `pipeline.md#no-subagents`).

Инцидент: нет

### Предел роли: исполнитель стадии не перестраивает конвейер `[ревью: PM @ барьер стадии]`
<a id="role-limit"></a>

Исполнитель стадии никогда не меняет исполнителя стадии и не перестраивает конвейер: `multica issue assign`, смена статуса чужой карточки, создание подзадач вне собственного круга ревью — полномочия PM. Упёрся в предел роли — стоп: комментарий с обоснованием и передаточной постановкой (кто / что / критерии приёмки); задача остаётся на исполнителе, пока PM не решит.

Инцидент: нет
