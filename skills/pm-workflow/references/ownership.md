# Что решает только владелец; эскалации; доклад владельцу

Слой 2 регламента воркспейса. Формат правила — `README.md`; адрес правила — `ownership.md#<якорь>`. Источники текста: снимок инструкций PM на 18.09.2026 (в приватном архиве; раздел Boundaries), файл проекта-источника `docs/engineering/pm-workflow.md` §6–§7, скилл `agent-runtime-gotchas` (перенесённые правила).

### `done` на родителе — только владелец `[ревью: PM @ приёмка]`
<a id="parent-done"></a>

`done` на родителе ставит владелец. PM доходит максимум до `in_review`. Подзадачи стадий — наоборот, закрываются исполнителем в `done` (`pipeline.md#barrier-terminal`).

Инцидент: нет

### Изменение объёма — владелец `[ревью: PM @ барьер стадии]`
<a id="scope-change"></a>

Изменение scope не решают ни PM, ни Architect. Находка требует переработки объёма — стоп независимо от счётчика кругов; PM и Architect готовят варианты, решает владелец. Карточку по ходу не расширять: работа не влезла — соседняя карточка.

Инцидент: нет

### `accepted-risk` и `spun-out` — решение владельца `[ревью: PM @ закрытие круга]`
<a id="exceptions-are-owner"></a>

Коды исключений реестра `accepted-risk` и `spun-out` ставятся только по решению владельца (реквизиты — `review-cycle.md#exception-codes`); PM исполняет (создаёт вынесенную карточку, пишет id), но не решает. Исключение — класс `гигиена`: реквизит = решение о классе (`impact-class.md#hygiene`).

Инцидент: нет

### Класс влияния под сомнением — вопрос владельцу до стадии 1 `[ревью: PM @ создание родителя]`
<a id="class-doubt"></a>

Сомнение в классе влияния — вопрос владельцу до старта первой стадии, не после круга.

Инцидент: [I](incidents.md#inc-i).

### Два PR на один дефект — технический вердикт, не мерж обоих `[ревью: Architect @ технический вердикт]`
<a id="two-prs"></a>

Когда два исполнителя чинят один дефект разными подходами, мерж обоих даёт конфликт на пересобранных артефактах, который руками не разрешается (замер: 44 тысячи строк). Заводится технический вердикт (`roles.md#roles-table`): какой подход держим; второй PR закрывается без мержа со ссылкой на вердикт. PM не решает это единолично, если PR принадлежит чужой карточке: у неё свой владелец и свой конвейер.

Инцидент: нет

### Эскалация к владельцу вместо лечения брифами `[ревью: PM @ барьер стадии]`
<a id="escalation"></a>

К владельцу, а не в бриф: серия инфраструктурных падений в одну минуту у разных агентов (не лечить брифами, не перезапускать круги руками — `agent-runtime-gotchas`, раздел B); модель непроверяема (пустой учёт — строку scorecard пометить недостоверной, не гадать); скилл потерял содержимое — не восстанавливать по памяти: эталон искать в задаче, где текст применяли, и сливать с фактами после потери; потеря без источника — к владельцу: запись прошла мимо конвейера и повторится.

Инцидент: нет

### Чего не делать `[ревью: PM @ комментарий]`
<a id="do-not"></a>

- Не спрашивать владельца о том, что уже решено и записано: историю (`CHANGELOG.md`, постановки, комментарии карточек, `AGENTS.md` проекта) читать до вопроса.
- Не заводить карточку, не поискав дубль.
- Не обещать проверок, которых нет, — ни в коде, ни в документах, ни в отчёте.
- Не расширять карточку по ходу (`#scope-change`).
- Не переписывать историю чужой ветки и не переключать ветку в общем дереве (`pipeline.md#one-writer`).
- Не выдавать рассуждение за замер: не проверено — так и написать.

Инцидент: нет

### Доклад владельцу: итог, цена, вопрос `[ревью: PM @ комментарий приёмки]`
<a id="owner-report"></a>

Коротко: итог, цена, вопрос; подробности — по встречному вопросу. Фактами и числами, не оценками: «гейт зелёный» без чисел — не отчёт; «573 файла, 9655 кейсов, ноль упавших, ноль пропущенных» — отчёт. Отдельной строкой — чего машина не проверяет (правдивость переводов, вид экрана, поведение чужого сервиса): это остаётся владельцу, и он должен видеть список, а не догадываться. Ошибся — сказать прямо и коротко, без самобичевания, и продолжить.

Инцидент: нет
